### Task 4: Foreign Key Actions

Consider the following scenario using the schema from Theory Section 9.8:

1. You want to delete category 2 ("Camping") from the `categories` table. Products 102 and 106 reference this category. What happens with:
   - `ON DELETE RESTRICT`?
   - `ON DELETE CASCADE`?
   - `ON DELETE SET NULL`? (Assume `category_id` in `products` allows NULL for this question)
  
> [!NOTE]
> ***Your Answer***
>
> *(

ON DELETE RESTRICT: The deletion will fail. The database will block the action and return an error because products 102 and 106 still reference this category, preventing orphaned records.

ON DELETE CASCADE: The deletion will succeed, and products 102 and 106 will also be automatically deleted. The deletion cascades down to any referencing rows.

ON DELETE SET NULL: The deletion will succeed. Products 102 and 106 will remain in the products table, but their category_id values will be automatically updated to NULL (making them uncategorized).
> )*
>
>
>

**Q1.** Define the following terms in your own words: relation, tuple, attribute, domain. Give one TrailShop example for each.

> [!NOTE]

A candidate key is any minimal set of attributes that uniquely identifies every row in a table. The primary key is simply the one candidate key that the database designer officially chooses to identify the rows. **Q6.** What is a NULL value? Why is `WHERE price = NULL` wrong? What should you write instead?


> [!NOTE]
> ***Your Answer***

> *(

A NULL value represents an unknown, missing, or inapplicable piece of data—it is not zero or an empty string. > ***Your Answer***
>
> *(

A junction table (or linking table) is used to resolve a many-to-many (M:N) relationship by splitting it into two one-to-many (1:N) relationships. It is needed because relational databases cannot directly connect many rows in one table to many rows in another. An example is the order_items table, which bridges the many-to-many relationship between orders and products.

**Q8.** Describe the three types of relationships (1:1, 1:N, M:N). For each, give one TrailShop example.

> [!NOTE]
> ***Your Answer***
>
> *(

1:1 (One-to-One): One row in Table A relates to exactly one row in Table B. Example: One product relates to one product_details row.
1:N (One-to-Many): One row in Table A relates to many rows in Table B. Example: One category contains many products.
M:N (Many-to-Many): Many rows in Table A relate to many rows in Table B. Example: products can have many tags, and a tag can apply to many products.

**Q9.** What is the difference between `ON DELETE CASCADE` and `ON DELETE RESTRICT`? When would you use each?


> [!NOTE]
> ***Your Answer***
>
> *(

ON DELETE CASCADE automatically deletes any dependent referencing rows when a parent row is deleted, while ON DELETE RESTRICT blocks the deletion of the parent row entirely if dependent rows still exist. Use RESTRICT for critical entities (like preventing a category from being deleted if products are in it) and CASCADE when dependent data has no value without the parent (like deleting order_items when an order is deleted).

### Exercise 3.1: Predict the Outcome

Given the following table definitions:

```sql
CREATE TABLE departments (
    dept_id   INTEGER      PRIMARY KEY,
    dept_name VARCHAR(50)  NOT NULL UNIQUE
);

CREATE TABLE employees (
    emp_id    INTEGER       PRIMARY KEY,
    name      VARCHAR(100)  NOT NULL,
    salary    NUMERIC(10,2) NOT NULL CHECK (salary >= 0),
    dept_id   INTEGER       NOT NULL REFERENCES departments(dept_id)
);
```

Assume these rows already exist:

```sql
INSERT INTO departments VALUES (1, 'Engineering');
INSERT INTO departments VALUES (2, 'Marketing');
INSERT INTO employees VALUES (100, 'Alice', 75000, 1);
INSERT INTO employees VALUES (101, 'Bob', 65000, 2);
```

For each statement below, predict: **SUCCESS** or **FAIL**? If fail, name the violated constraint.

```sql
-- 1
INSERT INTO employees VALUES (102, 'Carol', 70000, 1);

ans:SUCCESS. All constraints are met. The emp_id is unique, the name is provided, the salary is > 0, and dept_id 1 exists.

-- 2
INSERT INTO employees VALUES (103, 'Dan', -5000, 1);

ans:FAIL. Violates the CHECK constraint on salary (salary >= 0).

-- 3
INSERT INTO employees VALUES (100, 'Eve', 80000, 2);

ans:FAIL. Violates the PRIMARY KEY constraint. emp_id 100 already exists in the table (Alice).

-- 4
INSERT INTO employees VALUES (104, 'Frank', 60000, 5);

ans: FAIL. Violates the FOREIGN KEY constraint. dept_id 5 does not exist in the departments table.

-- 5
INSERT INTO departments VALUES (3, 'Engineering');

ans:FAIL. Violates the UNIQUE constraint on dept_name. 'Engineering' is already used by dept_id 1.

-- 6
INSERT INTO employees VALUES (105, NULL, 55000, 2);
ans: FAIL. Violates the NOT NULL constraint on the name column.

-- 7
DELETE FROM departments WHERE dept_id = 1;
ans:FAIL. Violates the FOREIGN KEY constraint. You cannot delete the Engineering department because an employee (Alice, emp_id 100) is still referencing it, which would create an orphan record.

-- 8
INSERT INTO employees VALUES (106, 'Grace', 0, 2);
ans: SUCCESS. A salary of 0 is valid because the constraint is CHECK (salary >= 0).
```

### Exercise 3.2: Write the Constraints

Given these business rules for a **bookstore database**, write the `CREATE TABLE` statements with appropriate constraints:

1. Every book has a unique ISBN (13 characters), a title (required), a price (must be positive), and a publication year.
2. Every author has an ID, a first name (required), and a last name (required).
3. A book can have multiple authors, and an author can write multiple books.
4. Every book belongs to exactly one genre. Genres have an ID and a unique name.
5. Publication year must be between 1450 and the current year.

*(Hint: you'll need at least 4 tables, including a junction table for the M:N relationship.)*
---

-- 1. Create Genres table first (so Books can reference it)
CREATE TABLE genres (
    genre_id INTEGER PRIMARY KEY,
    name VARCHAR(50) NOT NULL UNIQUE
);

-- 2. Create Authors table (so the junction table can reference it)
CREATE TABLE authors (
    author_id INTEGER PRIMARY KEY,
    first_name VARCHAR(100) NOT NULL,
    last_name VARCHAR(100) NOT NULL
);

-- 3. Create Books table (references genres)
CREATE TABLE books (
    isbn VARCHAR(13) PRIMARY KEY,
    title VARCHAR(255) NOT NULL,
    price NUMERIC(10,2) NOT NULL CHECK (price > 0),
    pub_year INTEGER CHECK (pub_year >= 1450 AND pub_year <= EXTRACT(YEAR FROM CURRENT_DATE)),
    genre_id INTEGER NOT NULL REFERENCES genres(genre_id)
);

-- 4. Create Junction Table for the M:N relationship (references books and authors)
CREATE TABLE book_authors (
    isbn VARCHAR(13) REFERENCES books(isbn),
    author_id INTEGER REFERENCES authors(author_id),
    PRIMARY KEY (isbn, author_id)
);
